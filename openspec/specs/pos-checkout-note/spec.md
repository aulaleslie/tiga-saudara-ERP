## Requirements
### Requirement: POS checkout provides an optional transaction note
The POS sell screen SHALL provide an optional transaction note field below customer selection and above the checkout action. The note SHALL accept at most 1,000 characters, and an empty or whitespace-only value SHALL be treated as no note.

#### Scenario: Cashier leaves the note empty
- **WHEN** a cashier completes a POS transaction without entering a transaction note
- **THEN** checkout proceeds without a note validation error

#### Scenario: Cashier enters a valid note
- **WHEN** a cashier enters a transaction note of at most 1,000 characters
- **THEN** the system stores the normalized note in the active POS cart

#### Scenario: Cashier enters an oversized note
- **WHEN** a cashier submits a transaction note longer than 1,000 characters
- **THEN** the system rejects the note update with an actionable validation message

### Requirement: POS transaction notes survive cart and draft round trips
The system SHALL return the current note in the POS cart snapshot and SHALL preserve it when the browser reloads, when the cart is saved as a POS transaction draft, and when that draft is loaded again.

#### Scenario: Cart reload preserves note
- **WHEN** a cashier saves a note in an active cart and reloads the POS page
- **THEN** the cart snapshot and note field display the same normalized note

#### Scenario: Saved draft restores note
- **WHEN** a cart with a note is saved as a POS transaction draft and later loaded
- **THEN** the loaded cart contains the same note

#### Scenario: Legacy draft has no note
- **WHEN** a draft created before this capability is loaded
- **THEN** the system treats its note as null and loads the draft successfully

### Requirement: Completed POS records preserve the transaction note
On successful finalization, the system SHALL copy the final cart note to the completed POS transaction and its POS checkout ledger. The note SHALL participate in draft snapshot drift detection and checkout idempotency comparison.

#### Scenario: Checkout persists final note
- **WHEN** a cart with a note is finalized successfully
- **THEN** the completed POS transaction and POS checkout store the same note

#### Scenario: Idempotency key is reused with a different note
- **WHEN** a checkout idempotency key is replayed with cart content that differs only by transaction note
- **THEN** the system rejects the conflicting payload instead of returning or creating a checkout for the different note

### Requirement: Every generated Sale receives the POS transaction note
The system SHALL copy a non-empty POS transaction note to every Sale generated by checkout posting and SHALL retain the existing POS checkout provenance in each Sale note. When no cashier note is present, the system SHALL retain the current provenance-only Sale note behavior.

#### Scenario: Inline posting copies note
- **WHEN** a POS checkout with a note generates one Sale
- **THEN** that Sale note contains the cashier note and the POS checkout provenance

#### Scenario: Split posting copies note to all Sales
- **WHEN** a POS checkout with a note generates multiple owner-aligned Sales
- **THEN** every generated Sale note contains the same cashier note and its POS checkout provenance

#### Scenario: Checkout has no cashier note
- **WHEN** a POS checkout without a cashier note generates one or more Sales
- **THEN** every generated Sale retains the existing POS checkout provenance without an empty note line
