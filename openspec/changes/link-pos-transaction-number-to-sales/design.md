## Context

A POS checkout produces one Sale (inline posting) or N Sales (split posting, one per owner/tax bucket). The linkage is already recorded in the `pos_checkout_sales` pivot, which stores `pos_checkout_id`, `split_key`, `sale_id`, `source_setting_id`, `source_location_id` and `tax_bucket`. Nothing consumes this pivot for navigation today.

The only user-visible trace of the linkage is `Sale.note`, written by `InlinePosCheckoutPostingAdapter` as `POS checkout #<checkout id>` — an internal primary key, not the `PosTransaction.code` that staff see everywhere else in the POS module.

Two constraints dominate this design:

**Ordering.** Inside `FinalizePosCheckoutService::finalize`, the Sale (and its note) is created at L957 via `postingAdapter->post()`, but the `PosTransaction` that owns `code` is only created at L1137 via `completeFromCartSnapshot`. The code does not exist when the note is written. Both calls are inside one DB transaction, so the fix is a sequencing concern rather than a consistency one.

**Setting scope.** `SaleController::show` calls `ensureSaleBelongsToCurrentSetting`, which `abort(404)`s when `sale.setting_id !== session('setting_id')` unless the user holds `globalSalesSearch.access`. Split posting deliberately creates Sales in other settings — `pos_checkout_sales.source_setting_id` records exactly that — so any Sale viewer reached from POS must not be setting-scoped, or it will 404 on the rows this feature exists to surface.

## Goals / Non-Goals

**Goals:**

- `Sale.note` carries the human-facing POS transaction code plus the cashier note.
- The Sales list displays and searches by POS transaction number, resolved through the pivot.
- POS transaction detail lists its generated Sales, each opening a read-only modal in place.
- The modal works across settings without weakening tenant isolation into a general bypass.
- The receipt leads with the transaction code; the receipt number is demoted but still legible.
- Return lookup accepts the transaction code, so demotion does not strand returns.

**Non-Goals:**

- Backfilling historical `Sale.note` values. Old rows keep `POS checkout #<id>`; display resolves through the pivot instead of parsing note text.
- Collapsing `receipt_number` and `code` into a single sequence. That is the right end state but pulls in returns, session summary and reprint; this change only reorders their prominence.
- Fixing the `receipt_number` uniqueness gap (indexed, not unique, generated by string sort without a lock). Pre-existing; noted as a risk.
- Adding a denormalized `pos_checkout_id` column to `sales`. The pivot is sufficient.

## Decisions

### 1. Pre-generate the transaction code, do not reorder side effects

Three options were considered for making the code available at posting time:

| Option | Effect | Verdict |
|---|---|---|
| Move `completeFromCartSnapshot` before posting | Cleanest read, but relocates a load-bearing call with line persistence and status transitions inside the most delicate service in the module | Rejected — blast radius |
| Backfill notes after L1137 | Minimal reordering, but writes every Sale twice and leaves a window where the note is wrong | Rejected — double write |
| Pre-generate only the code string, thread it through | One value computed early, passed into the adapter context and reused at L1137 | **Chosen** |

`PosTransactionCodeGenerator` is already a standalone injectable service whose `generate(int $settingId)` has no side effects beyond reading existing codes — it does not insert. Calling it earlier is safe.

`completeFromCartSnapshot` gains an optional `?string $presetCode` parameter used in place of `$this->codeGenerator->generate($settingId)` at its creation branch.

### 2. Resolve the code for an *existing* transaction before generating a new one

`completeFromCartSnapshot` only generates a code when `active_transaction_id` is absent; when a saved draft is being checked out, it reuses that transaction and its existing code. The pre-generation step must mirror this, or checking out a loaded draft would put a freshly minted, never-persisted code into the Sale note while the transaction kept its original.

Resolution order at pre-generation time:

```
active_transaction_id present?
  ├─ yes → SELECT code FROM pos_transactions WHERE id = ? AND setting_id = ?
  │         └─ found → use it
  └─ no / not found → codeGenerator->generate(settingId)
```

The same resolved value is passed to the adapter and to `completeFromCartSnapshot`, guaranteeing note and transaction agree.

### 3. Note format: code line, then cashier note

`Sale.note` becomes:

```
POS <code>
<cashier note>          ← omitted entirely when there is no cashier note
```

This preserves the existing shape (provenance line, newline, note) so the split adapter's per-group delegation and the "no blank suffix when note absent" behaviour carry over unchanged. The cashier note remains the raw value with no prefix, satisfying the clean-note requirement; the provenance line is a separate line, and UI that wants only the cashier note reads `PosTransaction.note` rather than parsing the Sale note.

### 4. Authorize the Sale modal by pivot reachability, not by setting

The modal endpoint is namespaced under the checkout, not under Sales:

```
GET /pos/checkouts/{checkout}/sales/{sale}
  1. permission check on POS checkout viewing
  2. authorize the *checkout* (its own setting / session ownership)
  3. assert $sale->id IS IN $checkout->checkoutSales()->pluck('sale_id')   ← the gate
  4. render read-only; no ensureSaleBelongsToCurrentSetting call
```

Step 3 is what makes skipping step 4 defensible: an arbitrary `sale_id` cannot be substituted, because only Sales this checkout provably generated are reachable. This is a narrow, auditable hole rather than a general unscoped Sale reader, and it mirrors the justification already accepted for `globalSalesSearch.access` — the user demonstrably transacted across those settings at this terminal.

Reusing `sales.show` with a relaxed guard was rejected: it would weaken isolation for every caller of that route, not just POS-originated ones.

### 5. Sales list resolves the code by join, not by note parsing

`SaleTable` joins through `pos_checkout_sales` → `pos_checkouts` → `pos_transactions`. Search adds a `whereHas` over that path matching `pos_transactions.code` and `pos_checkouts.receipt_number`.

Parsing `POS <code>` out of the note was rejected: it would not match historical rows (which carry the old id format), and it makes display depend on a free-text field the user can influence.

Both `pos_checkout_sales.sale_id` and `pos_checkouts.receipt_number` are indexed, and `pos_transactions` has `unique(setting_id, code)`, so the join path is covered.

### 6. Receipt: promote code, demote number

`No. Struk` leaves the top meta table and is replaced by `No. Transaksi` carrying the code. The receipt number moves below the existing `.tail-print-history` footer as a new small, right-aligned, muted element (~7px against the footer's 8px). It stays on the slip because returns still accept it.

## Risks / Trade-offs

- **Pre-generating the code widens the window for a duplicate code** → `PosTransactionCodeGenerator` already has a retry loop and `pos_transactions` has `unique(setting_id, code)`; the whole finalize path is one DB transaction, so a collision fails the checkout atomically rather than producing a mismatched note.

- **A checkout could post Sales and then fail before the transaction is created**, leaving a note referencing a code no `PosTransaction` owns → Both operations are already in the same transaction; a failure rolls back the Sales too. No new exposure.

- **`pos_checkouts.pos_transaction_id` is nullable and historical rows predate this change** → The POS column and modal must degrade to `-` rather than error. Requires explicit null handling and a test for legacy rows.

- **Unscoped Sale read is a deliberate isolation exception** → Constrained to pivot-reachable Sales and namespaced under the checkout route so it cannot be repurposed. Needs a negative test asserting a non-reachable `sale_id` is rejected.

- **Demoting the receipt number to ~7px on thermal paper is marginally legible** → Mitigated by return lookup accepting the transaction code, which is printed prominently; the receipt number becomes the fallback rather than the primary key staff must read.

- **`receipt_number` is not unique and is generated by string sort without a lock** → Pre-existing and out of scope, but more consequential now that it is a fallback lookup key. Return lookup by receipt number should handle multiple matches deterministically rather than assuming one.

- **The Sales-list join adds a query path to a paginated, filtered table** → Uses indexed columns throughout; should be eager-loaded rather than resolved per row to avoid N+1.

## Migration Plan

No schema changes. All linkage columns and the pivot already exist.

Deploy is code-only and forward-compatible: historical Sales keep their old note text and simply resolve their POS column through the pivot like any other row. Rollback is a straight revert — no data written by this change needs undoing, since the only new persisted value is the note string on Sales created after deploy.

## Open Questions

- When return lookup matches a receipt number shared by more than one checkout (possible given the missing unique constraint), should it surface all matches or reject as ambiguous? Deterministic handling is required either way.
- Should the Sales list POS column link to the POS transaction detail page, or is showing the code as text sufficient for this change? Linking is the obvious complement to item 4's POS→Sales direction but is not strictly required by the stated goals.
