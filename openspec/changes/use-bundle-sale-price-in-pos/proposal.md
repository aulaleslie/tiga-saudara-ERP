## Why

POS bundle checkout still uses the legacy bundle add-on price model while Product Bundle and standard Sales now distinguish final bundle sale price from informational component prices. POS needs to use the configured final bundle sale price for customer-facing totals while preserving owner-split posting accuracy when bundled stock belongs to different businesses.

## What Changes

- Use `product_bundles.bundle_sale_price` as the POS bundled parent row billable unit price when a bundle is selected.
- Keep POS UI behavior unchanged apart from the parent row price value: bundle component prices remain internal context and are not shown as billable POS cart, checkout, receipt, or modal totals.
- Stop applying POS customer tier repricing to selected bundled rows; normal tier repricing continues for non-bundled rows.
- Treat bundle component informational prices as internal revenue allocation weights for POS split posting only.
- Allocate POS-generated Sales document revenue across parent residual and bundle component owners while keeping `sale_bundle_items` component rows non-billable context.
- Keep standard Sales create/update/show/print behavior unchanged by this POS proposal.
- Apply PKP included-tax extraction to POS bundle allocation amounts using the parent line/default tax context and the source owner's PKP state.
- Allocate stockless bundle component revenue to the first configured non-PKP sales-location source setting.

## Capabilities

### New Capabilities
- `pos-bundle-sale-price-allocation`: POS bundle pricing and owner allocation behavior for selected bundles using final bundle sale price and informational component allocation amounts.

### Modified Capabilities
- `pos-bundle-selection-checkout`: POS bundled cart rows use final bundle sale price and bypass customer tier repricing.
- `pos-checkout-split-posting`: POS split posting allocates bundled revenue by parent/component ownership while preserving exact checkout reconciliation.

## Impact

- Affected POS services: cart line pricing/repricing, checkout preflight/stock resolution context, split planning, and checkout posting adapters.
- Affected records generated by POS checkout: `sales`, `sale_details`, `sale_bundle_items`, `dispatch_details`, POS checkout split summaries, and payment allocations.
- Affected configuration dependencies: `product_bundles.bundle_sale_price`, `product_bundle_items.informational_item_price`, product active-setting sale price fallback, parent/default tax, and sales-location configuration ordering.
- Standard Sales runtime flows must not be modified as part of this change.
