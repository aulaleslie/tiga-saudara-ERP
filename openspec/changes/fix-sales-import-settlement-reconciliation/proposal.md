## Why

Sales import is rejecting valid historical paid invoices even when the visible CSV rows reconcile at source-invoice scope. The failures cluster around split-owner invoices, high-precision DPP/tax/discount exports, one-cent allocation drift, and invoice rows that may be processed without the complete source invoice context.

## What Changes

- Ensure sales import processes complete source invoices for reconciliation, including all pending rows sharing the same `no_faktur`, before owner sale creation.
- Make source-invoice document adjustment allocation deterministic at two-decimal money precision so owner canonical totals sum back to the source invoice total.
- Reuse one canonical owner sale total for sale header persistence, settlement validation, payment status, and payment row creation.
- Preserve current source-total precision guardrails while allowing already-authoritative `Lunas` source totals to absorb valid cent-level export artifacts.
- Add regression coverage for the observed invalid import shapes from `prompt.txt`, `prompt1.txt`, and `prompt2.txt`.
- No database schema changes and no rewrite of historical imported records.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `import-split-owner-payment-allocation`: Sales split-owner invoice rows must be reconciled with complete source-invoice context, and owner settlement allocation must use canonical totals whose sum equals the authoritative invoice total.
- `import-document-total-reconciliation`: Sales document discount, shipping, and precision adjustments must be allocated at two-decimal precision without introducing owner-total rounding drift.
- `import-payment-ledger-consistency`: Sales import payment status, paid amount, due amount, and active payment rows must reconcile to the same canonical generated sale total used by final validation.

## Impact

- Affected code: `Modules/Sale/Services/SalesImportService.php`, `App\Support\ImportDocumentAdjustmentAllocator`, `App\Support\ImportSettlementAllocator`, and `App\Support\ImportPaymentSummaryResolver` if shared helper behavior needs a narrow compatibility update.
- Affected tests: focused sales import feature/unit coverage around invoice-complete chunking, split-owner discount allocation, zero-price accessory rows, one-cent source-total artifacts, and single-row exact reconciliation.
- Affected records: future imported `sales`, `sale_details`, `sale_payments`, `dispatches`, and `dispatch_details` generated by sales import.
- Out of scope: purchase import behavior changes, inventory import behavior changes, report UI changes, and repair of already-invalid historical batches.
