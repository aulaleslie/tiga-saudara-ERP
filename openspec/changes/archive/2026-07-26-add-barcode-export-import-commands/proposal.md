## Why

The team periodically cleans up production data with `php artisan migrate:fresh --seed`, which destroys every product row along with its id, code, and barcode. Barcodes are entered by hand through the "Kelola Barcode" workspace, one product at a time, and today there is no way to carry them across a cleanup — users must re-scan and re-enter every barcode afterwards.

Product ids and product codes are regenerated by the cleanup and cannot be used to reconnect a barcode to its product. Product name is the only stable identifier that survives, so a name-keyed export/import pair is the only viable way to preserve this work.

## What Changes

- Add `product:export-barcodes` — writes every product that currently has a barcode to a CSV keyed by product name, and reports the exported row count so the operator can verify the backup against the source table **before** running the destructive cleanup.
- Add `product:import-barcodes` — reads that CSV back after the cleanup and data imports have run, matching products by exact name and restoring barcodes into blank slots only.
- The reimport writes both `products.barcode` and a `barcode_identities` registry row inside a single transaction, so the barcode uniqueness registry stays consistent with the column.
- The reimport never overwrites an existing barcode. Every row it cannot apply is skipped and reported by category (`not_found`, `ambiguous`, `has_barcode`, `barcode_taken`), with a summary count per category.
- A `--dry-run` flag performs all matching and reporting with zero writes, so the operator can review the outcome before committing.
- No database migrations. No changes to any existing import service, and no changes to the interactive barcode workspace.

- `product-barcode-backup-restore`: Console commands that export product barcodes to a name-keyed file and restore them after a destructive database cleanup, including exact-name matching rules, fill-blanks-only semantics, registry consistency, and skip-and-report outcomes.

## Impact

**New code**
- `Modules/Product/Console/ExportBarcodesCommand.php`
- `Modules/Product/Console/ImportBarcodesCommand.php`
- Command registration in the Product module service provider.

**Read/written at runtime**
- `products.product_name`, `products.barcode` (read on export; barcode written on import).
- `barcode_identities` (registry row written alongside each restored barcode).
- `Modules\Product\Utils\BarcodeUtils::canonicalize` is reused to derive `canonical_key`.

**Deliberately not touched**
- `ProductBarcodeAssignmentService::assign()` is **not** reused. It requires an authenticated `User` and checks the `products.barcodes.manage` permission, neither of which a console command has; it also writes audit rows and uses replace semantics that are wrong for a bulk restoration of prior state.
- No `ProductBarcodeAssignment` audit rows are written — these are restorations of previously recorded state, not new assignments.
- `product_unit_conversions.barcode` is out of scope: only base product barcodes exist in production.
- Product identity is global, so no query is scoped by `setting_id`.

**Operational risk**
- The export file is the **only** copy of the barcodes once the cleanup runs. The count reported by the export exists specifically so the operator can verify the file before proceeding to an irreversible step.
- The unique indexes on `products.barcode` and `barcode_identities.canonical_key` are already active when the reimport runs, so constraint violations must surface as reported skips rather than crashing the run.

**Intended operator sequence**
1. `product:export-barcodes` (verify reported count against the source table)
2. `php artisan migrate:fresh --seed`
3. Run the usual data imports
4. `product:import-barcodes --dry-run` (review the projected outcome)
5. `product:import-barcodes` (review the skip report)
