## 6. Sequence 10 Correction — Split-Owner Carrier-Row Component Resolution

Discovered AFTER Phases 2–4 were marked complete, via production transaction TPI-TXN-2026-08-0024: `InlinePosCheckoutPostingAdapter` never creates a standalone `SaleDetails` row keyed by a cross-owner bundle component's own `product_id`. Instead the component owner's Sale gets a zero-quantity "carrier" `SaleDetails` row keyed by the PARENT's product_id, with a `SaleBundleItem` (component identity) and the component's own `DispatchDetail` both attached via `sale_detail_id` = that carrier row's id. Code that assumed a standalone same-Sale sibling row (the pre-existing convention for same-owner bundles) silently failed to resolve — or misattributed identity — for this shape.

- [x] 6.1 Rewrite `PosReturnSnapshotService::findComponentBundleItem()`/`resolveCatalogBundleComponents()`/`buildComponentBundleItemEntry()` to resolve a component's `SaleBundleItem` across every checkout sale (never assuming it lives under the parent's own Sale), disambiguated by `bundle_item_id` → `bundle_id` → exact `quantity_per_bundle`, blocking (returning null) rather than guessing when still ambiguous. (Fixed in an earlier session; verified still correct this session.)
- [x] 6.2 Extract the shared disambiguation/carrier-resolution logic into `Modules\Pos\Services\PosBundleComponentResolver` (`findComponentBundleItem()`, `findComponentDispatchDetailId()`, `resolveCatalogBundleComponents()`) and have both `PosReturnSnapshotService` and `PosReturnSubmissionService` delegate to it, so the two call sites can never disagree about what counts as ambiguous.
- [x] 6.3 Rewrite `PosReturnSubmissionService::synthesizeBundleCashReturnComponents()`/`synthesizeSerialComponentLines()`/`assertBundleCashReturnCompleteness()` to resolve each catalog component's `SaleBundleItem` across the checkout (narrow parent-sale scope first, widening to the full checkout only when unresolved — required to disambiguate a serialized parent with quantity > 1, where the same bundle catalog is purchased once per unit/Sale), and to explicitly persist the component's own `product_id`/`product_name`/`product_code`/`dispatch_detail_id` on synthesized `PosReturnLine`s rather than ever re-deriving identity from the carrier row's own (parent's) `product_id` column.
- [x] 6.4 Fix `PosReturnApprovalPreviewPlannerService::buildLinePlan()`'s `source_identity_mismatch` check, which compared the carrier `SaleDetails.product_id` (the parent's) against the persisted `PosReturnLine.product_id` (the component's own) and would always spuriously reject a cross-owner component line — excluded `product_id` from the identity check specifically for bundle-component lines (`sale_id` match is still required).
- [x] 6.5 Verify `PosReturnApprovalPlanPersistenceService` and `PosReturnLifecycleService` need no changes: both already read component identity from the persisted `PosReturnLine`/planner-derived `plannedDetail` fields (`product_id`, `sale_detail_id`, `component_sale_bundle_item_id`) rather than re-deriving from the carrier row's own columns.
- [x] 6.6 Preserve the "component-only cash return is prohibited" invariant (`assertBundleCashReturnCompleteness()` orphan-component detection) and confirm `bundle-component-controls.blade.php` is unaffected (still only offers `none`/`product_replacement` for components).
- [x] 6.7 Preserve legacy/hand-built fixture compatibility: when no catalog `ProductBundle` is resolvable, or a catalog component has no discoverable allocation (same-owner shape with no zero-priced sibling row, and no genuine cross-owner carrier), that component is excluded from "expected" entirely — never surfaced as a false "missing/incomplete" rejection — matching pre-correction behavior exactly.
- [x] 6.8 Run `php artisan test --filter=POSReturn` after the fix: 241 passed, 1269 assertions (up from the 239/1235 pre-fix baseline — the 2 new `POSReturnSplitOwnerCarrierRowRegressionTest` cases account for the difference; no regressions, no failures). Independently re-verified. `POSSplitSerialBundleCheckoutTest` (does not match the `POSReturn` filter) run separately: 9 passed, 110 assertions, unaffected.

## 7. Sequence 11 Correction — Close the Carrier-Row Refundable-Quantity Guard Gap

Closed the "known gap" flagged at the end of Sequence 10: `PosReturnQuantityGuard::getRefundableQuantity()` and every one of its call sites derived a bundle component's "original quantity" from `SaleDetails::quantity` of whatever `sale_detail_id` was passed — always 0 for a carrier row by construction, so the guard always evaluated a cross-owner (or same-owner-with-sibling) component's refundable quantity as 0, spuriously blocking any nonzero component cash return once actually exercised end-to-end.

- [x] 7.1 Extended `PosReturnQuantityGuard::getRefundableQuantity()` with an optional `$componentOriginalQuantity` parameter — when passed, used as the "original quantity" baseline instead of reading `SaleDetails::quantity`; already-cash-returned consumption remains scoped by `$saleDetailId` (the carrier row's id), a consistent accounting key since every synthesized/persisted component cash_return line for a given component is always keyed by that same carrier id.
- [x] 7.2 Threaded the component's true original quantity (`quantity_per_bundle × the bundle parent's own fully-refundable quantity`) into every `getRefundableQuantity()` call site that previously passed a carrier row id bare: `synthesizeBundleCashReturnComponents()`'s over-refund guard, `store()`'s and `update()`'s post-synthesis per-line re-validation loops, and `validateDraftLines()`'s pre-synthesis loop (the latter needed for `submitDraftForApproval()`'s re-validation of a previously-synthesized/persisted component line — see 7.3).
- [x] 7.3 Fixed `submitDraftForApproval()`'s persisted-line-to-raw-line remapping, which previously dropped every `__component_*`/`__bundle_parent_sale_detail_id` identity tag, causing a previously-synthesized component line to be re-processed on resubmit as if it were a standalone row (re-deriving identity from the carrier row's own product_id/always-0 quantity) — now carries `component_quantity_per_bundle`/`bundle_parent_sale_detail_id`/`product_id` forward as the same `__component_*` tags synthesis itself produces, disambiguated from a genuine parent line via `bundle_parent_sale_detail_id !== sale_detail_id`.
- [x] 7.4 Fixed the reassembly dedupe key in `synthesizeBundleCashReturnComponents()` (previously keyed only by `product_id`/live `SaleDetails.product_id`) to also check `__component_product_id`, so a resubmitted previously-synthesized component line correctly dedupes against this call's freshly re-synthesized line instead of producing a duplicate.
- [x] 7.5 Fixed `PosReturnReplacementGuard::validateReplacementSerial()`'s three call sites (`store()`, `update()`, `validateDraftLines()`), which previously passed the carrier row's own `product_id` (the parent's) for an independent, non-synthesized component `product_replacement` line — now use `$effectiveProductId`, resolved (when not already tagged by synthesis) from the returned serial's own authoritative `product_id`, since a serial can only ever belong to the product it was issued for.
- [x] 7.6 Fixed the same identity gap in `store()`'s/`update()`'s dispatch-detail resolution fallback (`DispatchDetail::where('sale_id', ...)->where('product_id', $saleDetail->product_id)`, which resolved the PARENT's dispatch instead of the component's) to use `$effectiveProductId`.
- [x] 7.7 Fixed `synthesizeSerialComponentLines()`'s original-serial lookup, which queried `ProductSerialNumber::where('dispatch_detail_id', $componentDispatchDetailId)` — always empty once an independent replacement has already executed for that component (the original serial's own `dispatch_detail_id` is cleared when it's received back as available stock) — added a fallback to the persisted lineage of a COMPLETED `product_replacement` `PosReturnLine` for that same `dispatch_detail_id`, whose `returned_serial_id` is the authoritative original serial identity (never guessed), letting `PosReturnSerialReplacementChainResolver` correctly chain forward to the current-held (replacement) serial.
- [x] 7.8 Extended `PosReturnApprovalPreviewPlannerService::isBundleComponentLine()` to also recognize an INDEPENDENT (non-synthesized) component line — which self-references `bundle_parent_sale_detail_id === sale_detail_id` (the same self-reference `store()` sets for any line whose `sale_detail_id` resolves to a row with `bundleItems`, including a carrier row) — via `component_quantity_per_bundle` being set plus the persisted `product_id` differing from the carrier row's own live `product_id`; without this, `source_identity_mismatch` always spuriously blocked a completed independent component replacement's later resubmission/preview.
- [x] 7.9 Persisted `component_quantity_per_bundle` (resolved from the catalog `ProductBundleItem`) on an independent, non-synthesized component line too, purely so 7.8's identity check can recognize it — never used to infer product identity itself (`$effectiveProductId`, from the returned serial, remains authoritative).
