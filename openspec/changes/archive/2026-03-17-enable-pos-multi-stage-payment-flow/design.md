## Context

The multi-stage payment infrastructure was built with the assumption that a `Sale` record (with `id` and `due_amount`) exists before checkout begins. However, in the actual POS flow, Sales are created **during** the finalize step. This architectural mismatch prevents the existing infrastructure from being activated.

The payment chain is persisted in the Laravel session under key `payment_chain_{identifier}` where `identifier` is used to track which cart's payments are being staged. The session stores committed SalePayments and calculates the remaining amount due. When finalize is called, it reads this session chain, normalizes it, and creates the Sale with all payment stages applied.

Current state:
- ✅ Frontend state machine and staged modal UI exist (`pos-staged-payment.js`)
- ✅ Backend API endpoints exist (`/api/pos/sell/checkout/stage-payment`, `/api/pos/sell/checkout/payment-chain`)
- ✅ Session chain structure and logic implemented in `PosCheckoutController`
- ❌ Not wired to the button (still opens old modal)
- ❌ Session key uses `sale_id` which doesn't exist yet
- ❌ Payment chain field names mismatch in normalization (`method_id` vs `payment_method_id`)
- ❌ Finalize call not triggered after payment completion

## Goals / Non-Goals

**Goals:**
- Activate the multi-stage checkout flow by wiring the button to the staged modal
- Support reload recovery: mid-transaction page reload resumes at the correct stage
- Support back-to-cart: users can abandon an uncommitted payment and return to the cart
- Use cart-scoped token (instead of Sale ID) as the session key so the flow works before Sale creation
- Fix the payment chain field name mismatch so finalize normalization works correctly
- Trigger finalize when all payment stages are complete (gratitude modal button)
- Make the transition transparent: same user experience across single-payment and multi-payment scenarios

**Non-Goals:**
- Modifying the finalize logic or payment allocation strategy
- Changing how Sales are created or structured in the database
- Redesigning the staged payment UI (HTML/CSS already done)
- Adding new payment methods or validation rules
- Implementing external payment gateway integration (EDC reference is manual entry only)

## Decisions

### 1. Use Cart-Scoped Token Instead of Sale ID

**Decision:** Generate a UUID on "Pilih Pembayaran" click, store it as `staged_payment_token` in the cart session, and use it as the payment chain session key (`payment_chain_{cart_token}`).

**Rationale:**
- Sale doesn't exist until finalize, so `payment_chain_{sale_id}` won't work
- A cart-scoped token is unique per checkout session and survives page reload
- The token can be returned in `cartSnapshot` so the UI always knows it
- When finalize is called with `cart_token`, the controller reads `payment_chain_{cart_token}` and creates the Sale
- Cleaner separation: token identifies the cart/checkout context, not the Sale

**Alternative considered:** Use PosTransaction ID if "Simpan dan Buka Baru" has been clicked. Rejected because fresh carts don't have a transaction, so this is incomplete for the common path.

### 2. Store Token in Cart Session, Return in Snapshot

**Decision:** Add `staged_payment_token` as a regular field in the cart session (in `PosCartSessionStore`), return it from `cartShow` endpoint via `buildSnapshot()`, reuse it on reload.

**Rationale:**
- Cart snapshot is already returned on every cart operation
- Token survives reload because it's in the server-side session
- No need for additional storage (localStorage, sessionStorage) with sync issues
- Clear single source of truth: cart session

**Alternative considered:** Generate UUID client-side, store in sessionStorage. Rejected because server needs to validate it exists on stage submission.

### 3. Generate Token on First Checkout Button Click

**Decision:** JavaScript generates `crypto.randomUUID()` when "Pilih Pembayaran" is first clicked. If `currentSnapshot.staged_payment_token` exists (reload case), reuse it; otherwise create new.

**Rationale:**
- Lazy generation: only create when needed
- Automatic reload recovery: token already in snapshot before reload
- No extra server round-trip needed
- Server can validate token was actually generated by checking session

**Alternative considered:** Server-side endpoint to generate token. Rejected as unnecessary overhead.

### 4. Field Name Mapping in checkoutFinalize

**Decision:** In `PosSellController->checkoutFinalize()`, when reading the session payment chain, map each entry from `{ method_id, amount, ... }` to `{ payment_method_id, amount_paid, ... }` before passing to `finalizeService->finalize()`.

**Rationale:**
- Session chain (from `PosCheckoutController->stagePayment()`) stores `method_id` and `amount`
- Normalization service expects `payment_method_id` and `amount_paid`
- Mapping in the controller keeps the services decoupled
- Centralized mapping point makes it explicit and testable

**Alternative considered:** Change `stagePayment()` to store normalized field names. Rejected because the session is the source of truth for API responses, and changing those responses would break existing client expectations.

### 5. Finalize Trigger: Gratitude Modal Button

**Decision:** The gratitude modal "Lanjut Jualan" button calls `POST /pos/sell/checkout/finalize` with `{ cart_token, idempotency_key }`.

**Rationale:**
- Finalize is the critical transaction point
- User sees gratitude/thanks screen before finalize
- Gives user a moment to confirm before committing
- Clear visual flow: pay → thank you → finalize → receipt
- If finalize fails, user is still in gratitude modal and can see error

**Alternative considered:** Auto-finalize when remainder = 0. Rejected because finalize is async, can fail, and should not happen silently behind a modal.

### 6. Reload Recovery: Check Session on Page Load

**Decision:** On DOMContentLoaded, if `currentSnapshot.staged_payment_token` exists, call `GET /api/pos/sell/checkout/payment-chain?cart_token=XXX` and auto-open staged modal if chain exists.

**Rationale:**
- Transparent to user: reload → modal pops back with correct state
- No extra click needed
- Checks session state (not client-side state) so it's always accurate
- If session expired, `has_chain: false` → normal POS state

**Alternative considered:** Show a "Resume?" banner. Rejected as UX friction.

### 7. Back to Cart: Close Button Only Before First Payment

**Decision:** The staged modal close button is shown only when `paymentChain.payments.length === 0`. When clicked, it calls `DELETE /api/pos/sell/checkout/payment-chain?cart_token=XXX` to clear the session, then closes modal and returns to cart.

**Rationale:**
- Once a payment is committed, it's in the session and database (SalePayment record)
- Allowing cancel after a commitment would require rollback logic
- Clarifying intent: close button = "I'm not paying yet", not "abort the transaction"
- User can always close and re-open modal to continue same chain

**Alternative considered:** Allow cancel anytime with rollback. Rejected as complex (reverses SalePayments, manages idempotency keys) and unclear UX.

## Risks / Trade-offs

| Risk | Mitigation |
|------|-----------|
| **Token collision** → two users generate same UUID | UUID v4 has 128-bit entropy; collision probability negligible. Session is per-user anyway. |
| **Session expires mid-payment** → user loses chain | Sessions are typically 24+ hours. If expires, reload recovery returns to POS (acceptable). Error message guides retry. |
| **Finalize fails after gratitude modal shown** → confusing UX | Finalize is synchronous in current design. If fails, error is shown in same modal. User can retry with same idempotency_key. |
| **User closes browser mid-payment** → chain orphaned in session | Session TTL handles cleanup. Not a data integrity risk (payments aren't committed until finalize). |
| **Field name mapping in checkoutFinalize is incomplete** → normalization fails | Add integration tests to verify field mapping works with all payment method types. |
| **Staged modal complexity vs old modal** → more code to maintain | Old modal was incomplete (no multi-stage support). Staged modal is the complete implementation. |
| **Token not returned in snapshot** → reload recovery breaks | Add test case for reload + verify token in snapshot. Build step can validate. |

## Migration Plan

**Phase 1: Deployment (No Breaking Change)**
- Deploy updated code with wired button + new staged flow
- Old modal remains in HTML but unreachable (button routes to new flow)
- No data migration needed (SalePayment schema unchanged)
- Session handling is pure software (no schema change)

**Phase 2: Testing**
- Manual QA: fresh cart → single payment, multi-stage, reload recovery, back to cart
- Integration tests for stage-payment endpoint with cart_token
- Test field name mapping in checkoutFinalize
- Load test: concurrent payment chains (one per session)

**Phase 3: Rollback (If Critical Issue)**
- Revert button to call old `openPaymentModal()`
- Old modal is still available and functional
- No data cleanup needed (session keys are ephemeral)
- Can roll back without affecting production data

## Open Questions

1. **Where to generate the token (client vs server)?** Currently planning client-side UUID on button click. Should we validate it server-side on first stage-payment call, or assume it's always valid?

2. **Session TTL for payment chains?** Current session TTL is ~24 hours. If a payment chain sits for hours, should we auto-clear it or let user resume? Suggestion: document expected behavior.

3. **Multi-user scenarios**: If user is logged in from two tabs and tries to pay in both, will they collide on `staged_payment_token`? (Each tab has separate snapshot, so should be isolated—but verify in testing).

4. **Error on stage-payment with invalid cart_token**: Should we auto-generate a new token and retry, or show error? Currently: show error (clearer UX).
