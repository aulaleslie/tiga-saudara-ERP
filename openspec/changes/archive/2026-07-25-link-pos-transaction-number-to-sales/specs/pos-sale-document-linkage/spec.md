## ADDED Requirements

### Requirement: Sales list displays the POS transaction number
The sales list SHALL display the POS transaction code for every Sale generated by a POS checkout, resolved through the POS checkout sales pivot rather than by parsing the Sale note. Sales not originating from POS, and POS-originated Sales with no linked POS transaction, SHALL render a neutral placeholder instead of an error.

#### Scenario: POS-originated Sale shows its transaction code
- **WHEN** the sales list renders a Sale linked to a POS checkout with a POS transaction
- **THEN** the row displays that POS transaction code

#### Scenario: Non-POS Sale shows a placeholder
- **WHEN** the sales list renders a Sale that did not originate from a POS checkout
- **THEN** the POS column displays a neutral placeholder

#### Scenario: Legacy POS Sale without a linked transaction
- **WHEN** the sales list renders a POS-originated Sale whose checkout has no linked POS transaction
- **THEN** the POS column displays a neutral placeholder without raising an error

#### Scenario: Historical Sale notes are not parsed
- **WHEN** the sales list renders a Sale whose note contains a legacy checkout-identifier provenance line
- **THEN** the displayed POS transaction code is resolved from the pivot, not from the note text

#### Scenario: Listing many POS Sales does not issue per-row queries
- **WHEN** a page of POS-originated Sales is listed
- **THEN** the POS transaction codes are resolved without issuing one query per row

### Requirement: Sales list search matches POS identifiers
The sales list search SHALL match Sales by POS transaction code and by POS checkout receipt number, in addition to the existing searchable fields. Matching SHALL be partial and SHALL preserve all existing search behavior.

#### Scenario: Search by full POS transaction code
- **WHEN** a user searches the complete POS transaction code of a POS-originated Sale
- **THEN** that Sale appears in the results

#### Scenario: Search by partial POS transaction code
- **WHEN** a user searches a fragment of a POS transaction code
- **THEN** Sales whose POS transaction code contains that fragment appear in the results

#### Scenario: Search by receipt number
- **WHEN** a user searches a POS checkout receipt number
- **THEN** every Sale generated by that checkout appears in the results

#### Scenario: Existing search fields still match
- **WHEN** a user searches by Sale reference, customer, product, tax reference or tag
- **THEN** results match as they did before POS search was added

#### Scenario: Split checkout search returns all generated Sales
- **WHEN** a user searches the POS transaction code of a checkout that generated multiple Sales
- **THEN** all Sales generated by that checkout appear in the results

### Requirement: POS transaction detail lists its generated Sale documents
The POS transaction detail view SHALL list every Sale document generated by that transaction's checkout, showing each Sale reference. When the checkout generated no Sales, or the transaction has no completed checkout, the view SHALL state that plainly rather than rendering an empty control.

#### Scenario: Single generated Sale
- **WHEN** a completed POS transaction generated one Sale
- **THEN** the detail view lists that Sale reference

#### Scenario: Split checkout lists every Sale
- **WHEN** a completed POS transaction generated multiple owner-aligned Sales
- **THEN** the detail view lists every generated Sale reference

#### Scenario: Draft transaction has no generated Sales
- **WHEN** a POS transaction has not been completed through checkout
- **THEN** the detail view indicates that no Sale documents exist yet

### Requirement: Generated Sale documents open in a read-only modal
Selecting a linked Sale reference on POS transaction detail SHALL open a read-only view of that Sale in a modal on the same page. The system SHALL NOT navigate away to the Sales module, and the modal SHALL NOT expose actions that modify the Sale.

#### Scenario: Opening the modal
- **WHEN** a user selects a linked Sale reference on POS transaction detail
- **THEN** a modal opens in place showing that Sale's details
- **AND** the browser does not navigate to the Sales module

#### Scenario: Modal is read-only
- **WHEN** the Sale detail modal is open
- **THEN** no control that edits, deletes, or otherwise mutates the Sale is presented

#### Scenario: Closing the modal
- **WHEN** the user dismisses the modal
- **THEN** the modal closes and the POS transaction detail page is unchanged

### Requirement: Linked Sale viewing is authorized by checkout reachability
The system SHALL authorize the read-only Sale view by verifying that the requested Sale is recorded as generated by the requested POS checkout, and SHALL NOT reject the request merely because the Sale belongs to a different setting than the viewer's current one. A Sale that is not reachable from the requested checkout SHALL be refused.

#### Scenario: Cross-setting Sale is viewable
- **WHEN** a user opens a Sale that its POS checkout generated in a different setting than the user's current setting
- **THEN** the read-only Sale detail is returned instead of a not-found response

#### Scenario: Unreachable Sale is refused
- **WHEN** a request pairs a POS checkout with a Sale that the checkout did not generate
- **THEN** the system refuses the request

#### Scenario: Caller lacking POS checkout access is refused
- **WHEN** a user without permission to view the POS checkout requests one of its generated Sales
- **THEN** the system refuses the request

#### Scenario: Access does not extend beyond the checkout
- **WHEN** a user is authorized to view Sales generated by one POS checkout
- **THEN** that authorization grants no access to Sales outside that checkout's generated set

### Requirement: Return lookup accepts the POS transaction code
Because the receipt number is de-emphasised on the printed receipt, POS return lookup SHALL locate a checkout by its POS transaction code in addition to its receipt number. Lookup by receipt number SHALL continue to behave as before. When an identifier matches more than one checkout, the system SHALL resolve the ambiguity deterministically rather than returning an arbitrary match.

#### Scenario: Lookup by POS transaction code
- **WHEN** staff enter a POS transaction code during return lookup
- **THEN** the corresponding checkout is located

#### Scenario: Lookup by receipt number still works
- **WHEN** staff enter a receipt number during return lookup
- **THEN** the corresponding checkout is located as it was before this change

#### Scenario: Unknown identifier
- **WHEN** staff enter an identifier matching neither a receipt number nor a POS transaction code
- **THEN** the system reports that no checkout was found

#### Scenario: Ambiguous receipt number
- **WHEN** an entered receipt number matches more than one checkout
- **THEN** the system resolves the ambiguity deterministically rather than silently selecting an arbitrary checkout

### Requirement: POS transaction detail displays the cashier note
The POS transaction detail view SHALL display the note captured at checkout as the raw cashier note, without any provenance prefix. When no note was captured, the view SHALL state that plainly.

#### Scenario: Transaction with a note
- **WHEN** a POS transaction detail view is opened for a transaction with a note
- **THEN** the raw cashier note is displayed without a provenance prefix

#### Scenario: Transaction without a note
- **WHEN** a POS transaction detail view is opened for a transaction with no note
- **THEN** the view indicates that no note exists
