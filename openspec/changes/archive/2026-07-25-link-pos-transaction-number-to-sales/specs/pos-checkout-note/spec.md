## MODIFIED Requirements

### Requirement: Every generated Sale receives the POS transaction note
The system SHALL copy a non-empty POS transaction note to every Sale generated by checkout posting and SHALL record the POS transaction code as provenance in each Sale note. The provenance line SHALL identify the checkout by its human-facing POS transaction code, not by an internal checkout identifier. When no cashier note is present, the system SHALL write the provenance line alone without a trailing blank line.

#### Scenario: Inline posting copies note
- **WHEN** a POS checkout with a note generates one Sale
- **THEN** that Sale note contains the cashier note and a provenance line carrying the POS transaction code

#### Scenario: Split posting copies note to all Sales
- **WHEN** a POS checkout with a note generates multiple owner-aligned Sales
- **THEN** every generated Sale note contains the same cashier note and the same POS transaction code provenance

#### Scenario: Checkout has no cashier note
- **WHEN** a POS checkout without a cashier note generates one or more Sales
- **THEN** every generated Sale note contains the POS transaction code provenance without an empty note line

#### Scenario: Sale note never exposes the internal checkout identifier
- **WHEN** any Sale is generated by checkout posting
- **THEN** the Sale note SHALL NOT contain the internal POS checkout primary key as its provenance identifier

## ADDED Requirements

### Requirement: The POS transaction code is resolved before Sales are posted
The system SHALL resolve the POS transaction code before generating any Sale document, so that the code is available when the Sale note is written. When the cart is a previously saved draft, the system SHALL reuse that draft's existing transaction code rather than generating a new one. The code written into Sale notes SHALL be identical to the code persisted on the completed POS transaction.

#### Scenario: Walk-up checkout with no saved draft
- **WHEN** a cart with no active transaction is finalized
- **THEN** a transaction code is generated before posting
- **AND** the completed POS transaction is persisted with that same code

#### Scenario: Checkout of a previously saved draft
- **WHEN** a cart loaded from a saved POS transaction draft is finalized
- **THEN** the existing draft transaction code is reused
- **AND** no new transaction code is generated

#### Scenario: Note and transaction agree
- **WHEN** a checkout completes successfully
- **THEN** the POS transaction code in every generated Sale note matches the code on the completed POS transaction record

#### Scenario: Posting failure leaves no orphaned code reference
- **WHEN** checkout posting fails after Sales are drafted but before the POS transaction is persisted
- **THEN** the whole checkout is rolled back so no Sale note references a non-existent transaction code
