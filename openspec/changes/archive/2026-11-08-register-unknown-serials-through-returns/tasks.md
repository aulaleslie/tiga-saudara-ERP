UAT scenario reference for Sales Return (standard) and POS Return:
1. Old sale of a product that was untracked at sale time and now requires serials: Create offers entry of unknown serials per unit; saving a draft creates NO serial, stock or history row.
2. Existing serial lookup: a serial already registered is rejected with guidance to use lookup; a serial from a historically serialized sale rejects any unknown serial.
3. Pending corrections: Edit changes, removes and re-adds proposed serials; unchanged values keep their claim; duplicates and wrong counts are rejected.
4. Receiving (standard) / approval (POS): serials are registered atomically in the correct owner location, tax bucket and held custody; sellable stock is unchanged until inspection release.
5. Collision: create the same serial elsewhere (purchase) before receiving; the whole receiving rolls back, the typed text is kept, and the user can correct and retry.
6. Split-owner bundle: whole-bundle cash return registers component serials under the component owner's location; confirm no parent-product serial is created.
7a. Split-owner component replacement, end to end: Create (whole-bundle replacement, proposed original + replacement serial per unit) -> Edit (reload pairing, change/clear a replacement, save) -> Approval preview (original shown as not yet registered, replacement shown) -> Approve (original registered in the component owner's location, replacement dispatched from that owner's stock and linked to the original, parent entitlement not consumed).
7. Repair/replacement then refund: a registered unit sent back (repair) or replaced can be returned again, and consumes the original quantity once; a partly returned multi-unit sale keeps the untouched units returnable.
8. Receipts/history: reprint a receipt after each scenario and confirm serials and return history match.
